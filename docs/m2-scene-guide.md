# M2 场景搭建指南 · 斜 45° 轻 3D

> 面向 **ly 在 Cocos Creator 3.8.8 编辑器里的操作**。
> 代码侧（`logic/` 与 `scripts/`）不在这份文档里，接口看 `game/assets/logic/API.md`。
>
> **这份文档的定位**：M2 的目标是「30 秒能玩完的最丑版本」。
> 下面每一条的取舍标准都是**「能不能玩」，不是「好不好看」**。
> 凡是写着「M2 不做」的，都不是忘了，是刻意推迟——理由都写在旁边。

---

## 0. 三条红线：越过去要付真金白银

这三条不是风格建议。每一条都对应 A5 已经实测出来的包体数字，越过去就白费。

| # | 红线 | 越界的代价 | 判据（构建后自己能查） |
|---|---|---|---|
| 1 | **任何节点都不许加物理组件**（`BoxCollider` / `RigidBody` / `SphereCollider` …） | 物理模块进包：ammo wasm 约 1.2 MB + js 约 0.7 MB。A5 已经确认物理被裁干净了，加一个组件就全回来 | 构建产物里 `grep -c "b2World\|PhysicsSystem\|ammo\|cannon"` 应为 **0** |
| 2 | **不开实时阴影**（方向光的 Shadow 不勾、场景 Shadows 不启用） | 移动端实时阴影是最贵的单项之一，而斜 45° 固定相机根本不需要它 | 见下面 §5 的 Blob Shadow |
| 3 | **不给 Skybox 指定 cubemap 贴图 / 不勾 HDR** | 850 KB。A5 那次它自己消失了，是因为新工程没引用；手动指定就会回来 | `pnpm size` 的 assets 那一栏应保持在 400 KB 上下 |

> ⚠ 第 1 条最容易犯——因为 Cocos 的教程几乎全在教你加 Collider。
> **这个项目的碰撞全部在 `logic/collision.ts` 里手写**，编辑器里的方块只是「看得见的形状」，
> 不参与任何判定。你在编辑器里加的 Collider 不会让游戏更对，只会让包更大。

**M2 还不做的**（不是遗漏）：后处理（Bloom / FXAA）· 光照烘焙（lightmap）· 任何贴图 ·
任何模型文件（`.fbx` / `.gltf`）· 音效 · 粒子。

## 1. 坐标系与单位：先把这个对齐，后面全省事

| 约定 | 值 |
|---|---|
| **1 世界单位 = 1 米** | 编辑器里 scale=1 的 Cube 就是 1 米见方 |
| **玩法平面是 XZ** | 角色只在 X 和 Z 上移动，**Y 恒定**。无跳跃、无斜坡、无楼层 |
| **地板在 y = 0** | 角色的 `position.y` = 半身高（固定值），不参与逻辑 |
| **厨房原点在地板中心** | `Kitchen` 节点放 `(0, 0, 0)`，所有工位坐标相对它 |
| **`logic/` 里的坐标是 `{x, z}`** | 没有 `Vec3`。组件负责在 `Vec3` 与 `{x,z}` 之间转，`logic/` 一侧永远只有两个分量 |

**按 1 米格子规划厨房，工位坐标全用整数或 0.5 的倍数。**
理由不是洁癖：我写单测时要手算「角色站在 (2, 3) 够不够得着灶台」，
坐标是 `2.37` 还是 `2` 决定了这个测试好不好写、将来出 bug 好不好查。

## 2. 场景层级：照这棵树建

### 2.0 先决定在哪个场景里搭：新建 `Main.scene`

工程里现在只有 `assets/test.scene` —— Cocos 新建 3D 项目给的默认场景，里面只有
`Main Light` 和 `Main Camera`，别的什么都没有。**别在它上面搭**：

- 这个场景要一路用到上线，主场景叫 `test` 不合适。将来改名要动 uuid 和 `.meta`，
  现在建对是零成本，M2 搭完再搬就是重来一遍
- `test.scene` 留着当**沙盒**更有用：试相机参数、试材质、挂 `A7Probe` 那类探针都在它里面干，
  不碰主场景。ROADMAP §6.5 定了「场景文件不 merge」—— `.scene` 是带 uuid 的 JSON，
  冲突了没法手动合，主场景越少动越安全

**步骤**：

1. 资源管理器选中 `assets` → 右键 → 创建 → 场景，命名 **`Main`**
2. 双击打开，照下面那棵树建
3. ⚠ **构建面板的「起始场景」改指到 `Main`** —— 漏了这步构建出来跑的还是 `test`，
   而 `test` 里只有灯和相机、**画面是空的**，很容易误判成「我搭的东西没进包」
4. `test.scene` 别删

**新场景建完立刻查这三条** —— 新建场景的默认值正好踩 §0 的红线：

| 查什么 | 该是什么 |
|---|---|
| `Main Camera` 的 `Projection` | 默认 PERSPECTIVE，要改 **ORTHO**（§3） |
| Skybox 有没有自带 cubemap | **没有**。A5 那 850 KB 天空盒就是这么进包的（§0 红线三） |
| `Main Light` 的 `Shadow Enabled` | **没勾**（§0 红线二） |

> 场景名用 `Main` 而不是游戏名：游戏名 M2 出口才定死（软著要它与上架名完全一致），
> 场景名与它解耦，定名之后不用回头改。

### 2.1 层级树

命名严格按 ROADMAP §6.2。**我看不见你的编辑器**，代码里的 `find()` 全按这套名字写，
对不上的时候是改名字不是改代码——代码有测试兜底，场景没有。

```
Scene
├── Main Camera            正交 · 斜 45° · 建好就锁住别再动
├── Main Light             DirectionalLight · Shadow 不勾
│
├── Kitchen                静态场景根（将来整块烘焙/合并 mesh 就靠它成一整块）
│   ├── Floor              地板（Plane 或压扁的 Cube）
│   ├── Wall_N             北墙
│   ├── Wall_W             西墙
│   ├── Station_Fridge     ← 冰箱
│   ├── Station_Grill      ← 烤炉
│   ├── Station_Assembly   ← 组装台
│   └── Station_Serve      ← 出餐口
│
├── Actors                 会动的东西都在这层
│   ├── Player
│   │   ├── Body           胶囊
│   │   ├── Head           球
│   │   ├── Anchor_Hand    空节点 · 头顶持有物的挂点（§6.2 的 Anchor_ 约定）
│   │   └── Shadow         贴地椭圆片
│   └── Customers          空节点 · 运行时往里生成，编辑器里留空
│
└── Canvas                 UI（2D）
    ├── UI_Joystick        摇杆的视觉（左半屏）
    ├── UI_ActionButton    动作键（右半屏）
    └── UI_HUD             订单/金币/计时
```

**为什么静态和动态要分两棵子树**：`Kitchen` 底下的东西这辈子都不动，
将来可以整块合并成一个 mesh、烘一张 lightmap；`Actors` 底下每帧都在变。
现在分好，M3 做优化时是拖一个节点的事；现在混在一起，那时候要一个个挑。

> ⚠ **只有两面墙**，不是四面。斜 45° 下有两面永远背对相机——建了也看不见，纯浪费。
> 这是 §2.3「白拿的东西」里那条「模型背面可直接删面」的最简版。
>
> **但哪两面取决于相机往哪个方向看，这一步先确认再建墙**：
>
> | 相机 Position | Rotation | 从哪看 | 该建的两面墙 |
> |---|---|---|---|
> | `(15, 15, 15)` | `(-35, 45, 0)` | 东南 → 西北 | **北 + 西**（`Wall_N` `Wall_W`）← 本文档 §2.3 按这个写 |
> | `(-10, 10, 10)` | `(-35, -45, 0)` | 西南 → 东北 | **北 + 东**（`Wall_N` `Wall_E`） |
>
> 第二行是 **Cocos 新建 3D 场景给的默认相机**。两者是镜像关系，都能用，
> 但**墙建错边的话它会正对镜头把整个厨房挡住**，而这要等你搭完才看得出来。
>
> 用第二种（默认相机）的话，§2.3 那套坐标**把所有 x 取负**即可 ——
> 工位之间的距离一个都不变，所以 `pnpm layout` 的难度判据照样过（镜像不改距离）。
> 改完记得同步 `tools/layoutcheck.ts` 顶上的 `PLACED`，跑一遍确认。

### 2.2 每个节点是什么东西：创建菜单对照表

上面那棵树只写了名字。**名字不决定节点是什么** —— Cocos 里一个节点身上挂了什么组件，
它就是什么。下面这张表是「层级管理器里右键 → 创建 → ？」的逐条答案。

| 节点 | 右键 → 创建 → | 建出来身上有什么 | 说明 |
|---|---|---|---|
| `Main Camera` | **不用建** | `Camera` | 新建场景自带 |
| `Main Light` | **不用建** | `DirectionalLight` | 新建场景自带 |
| `Kitchen` | 空节点 | 只有 Transform | 纯容器，放 `(0,0,0)` |
| `Floor` | 3D 对象 → **Cube** | `MeshRenderer` | 不要用 Plane，理由见下面「米尺」那条 |
| `Wall_N` / `Wall_W` | 3D 对象 → **Cube** | `MeshRenderer` | 压扁成长条，高 2.5 |
| `Station_*`（四个） | 3D 对象 → **Cube** | `MeshRenderer` | **必须是 Cube**，§8 的 AABB 从它的 `scale` 读 |
| `Actors` | 空节点 | 只有 Transform | 纯容器 |
| `Player` | 空节点 | 只有 Transform | 容器；M2 后期在它身上挂 `PlayerController` 脚本 |
| `Player/Body` | 3D 对象 → **Capsule** | `MeshRenderer` | 菜单里没有 Capsule 就用 Cylinder，M2 阶段角色只是个占位 |
| `Player/Head` | 3D 对象 → **Sphere** | `MeshRenderer` | |
| `Player/Anchor_Hand` | 空节点 | 只有 Transform | 纯挂点：持有物运行时挂到它下面 |
| `Player/Shadow` | 3D 对象 → **Plane** | `MeshRenderer` | 唯一该用 Plane 的地方（要的就是一张水平片），⚠ scale 见 §6 |
| `Customers` | 空节点 | 只有 Transform | 编辑器里就是空的，运行时往里生成 |
| `Canvas` | UI 组件 → **Canvas** | `Canvas` + `UITransform` + `Widget` | ⚠ 见下面「Canvas 会自带一个相机」 |
| `UI_Joystick` | UI 组件 → Sprite | `Sprite` + `UITransform` | 浮动摇杆，**默认 `active` 关掉**（见下） |
| `UI_ActionButton` | UI 组件 → Sprite | `Sprite` + `UITransform` | 别用 Button 组件，见下 |
| `UI_HUD` | 空节点 → **手动加 `UITransform`** | 只有 Transform | 容器，文字放它下面的 `Label` 子节点 |

> ⚠ **在 `Canvas` 底下建空节点，Cocos 不会自动给它 `UITransform`** —— 没有这个组件
> UI 系统根本不认这个节点（它不参与布局、`Widget` 也挂不上去），但场景里看起来一切正常。
> 建完手动 添加组件 → UI → `UITransform`。`pnpm scene` 会把缺它的节点报出来。
>
> ⚠ **改 UI 尺寸前先把 `Sprite` 的 `SizeMode` 改成 `CUSTOM`**。
> 新建的 Sprite 是 `TRIMMED`，contentSize 跟着图片走（内置白块是 40×36），
> 你在 `UITransform` 里填的宽高会被顶回去。

**判别法一句话**：画面上看得见的 = 3D 对象或 Sprite（身上有渲染组件）；
**看不见的一律是空节点** —— 空节点只有一个 Transform，不画任何东西，
它存在的价值就是「一个坐标 + 一组孩子」。`Kitchen` / `Actors` / `Customers` / `Anchor_Hand`
这四个都是这种，建出来在场景里什么都看不到是**对的**，不是建错了。

> ⚠ 这张表里**没有任何一个节点该加 Collider / RigidBody**（§0 红线一）。
> 编辑器里的 Cube 只是「看得见的形状」，碰撞判定全在 `logic/collision.ts` 手写。

#### ⚠ 先放一把「米尺」：内置几何体的默认尺寸并不都是 1 米

Cube 是 1×1×1，`scale` 填几就是几米，最省心。**但 Plane 不是** —— 它的内置 mesh
默认边长是 **10 米**，`scale = (0.8, 1, 0.6)` 出来的是 **8×6 米**，不是 0.8×0.6 米。
Capsule / Cylinder 的默认高度也不见得是 1。

判据（30 秒，一劳永逸）：

1. 建一个 `Cube`，`scale` 保持 `(1,1,1)` —— 这就是**一米**，命名 `_Ruler`
2. 每新建一种几何体，先把它拖到 `_Ruler` 旁边、`scale` 都保持 1，肉眼比一下真实尺寸
3. 场景搭完**把 `_Ruler` 删掉**（留着会跟着进包，也会污染 §11 的验收）

所以：**凡是尺寸要精确的（地板、墙、工位）一律用 Cube**，scale 就是米数，
不用做任何换算，代码那边读 `node.scale` 也直接是米（§8）。

#### ⚠ Canvas 会自带一个相机，别删也别改

创建 Canvas 时 Cocos 会自动在它下面生成一个 `Camera` 子节点，专管 UI，
`Canvas` 组件的 `Camera` 字段指着它。这个相机和 `Main Camera` 是两套：

- `Main Camera` 画 3D（厨房、角色），`ClearFlags` = `SOLID_COLOR`
- Canvas 底下那个画 UI，`ClearFlags` = `DONT_CLEAR`

**两个都别动**。改错的典型表现是「3D 没了只剩 UI」或者「UI 被 3D 盖住」，
而这两种现象看起来都像是层级摆错了，会往完全错的方向查。

#### 摇杆和动作键为什么是 Sprite，不是 Button

`input.ts` 的 `TouchRouter` 已经把整块屏幕按 `splitX` 分成左右两半自己路由触摸了
（左半屏是摇杆，右半屏是动作键），**它不需要 UI 控件来接事件**。
组件那边只做一件事：把 `touch-start/move/end` 的 `(id, x, y)` 原样喂进 `TouchRouter`。

所以这两个节点纯粹是**视觉指示**：

- `UI_Joystick` 是**浮动**摇杆 —— 手指按在左半屏哪里它就出现在哪里，
  所以它在编辑器里 `active` 应该是**关掉**的，按下时由脚本打开并移到手指位置
- `UI_ActionButton` 固定在右下角，只是让玩家知道「点这儿」，实际整个右半屏都能点

用 `Button` 组件反而会和 `TouchRouter` 抢事件，出现「点一次响应两次」。M2 就用纯 `Sprite`
（内置白块改个颜色即可，方的就方的 —— 这版本本来就是最丑的）。

#### `Player` 节点的原点建议放在脚底

即 `Player.position.y = 0`，`Body` / `Head` 在子节点里往上抬。
这样 `Shadow` 的 local `y` 就是 `0.01`（§6），改角色身高时不用回头重算阴影的偏移；
原点放腰上的话每次都要重算一遍。

`logic/` 那侧只认 `{x, z}`，`y` 取多少都不影响判定（§1），所以这条纯粹是省事，不是硬约束。

### 2.3 定稿数值：每个节点的 Transform

**照抄即可**。下面这套坐标不是拍脑袋的，是枚举出来再用 `sim.ts` 验过的 —— 出处见本节末尾。

#### 布局俯视（北在上 = -Z，西在左 = -X，相机从东南方向往下看）

```
        x=-4                                   x=+4
  z=-3  ┌────────────────────────────────────────┐  ← Wall_N
        │    ▓▓▓▓                      ▓▓▓▓      │
  z=-2  │    Grill                     Fridge    │
        │                                        │
  z=-1  │                                        │
        │  ▓▓▓▓                                  │
  z= 0  │Assembly       （中央全空）              │
        │  ▓▓▓▓                                  │
  z= 1  │ ↑贴西边界                               │
        │                                        │
  z= 2  │                  ▓▓▓▓▓▓▓▓              │
  z= 3  └──────────────────Serve─────────────────┘  ← 顾客在这条边外侧
                                          Wall_E ↑
```

> **一个连带的待决事项（等 `customer.ts`，别现在做）**：`Station_Serve` 贴在南边界上，
> 意味着顾客要站在 `z > 3`，也就是**地板外面**——现在摆进去会浮空。
> 三条路：往南加一块 `Floor_Customer`（比如 `(-1, -0.05, 4)`，scale `(6, 0.1, 2)`）／
> 把 `Floor` 整体往南延到 `z = 5`／顾客本来就站在店外不需要地板（很多同类游戏就这么做）。
> 这三种排队方向和镜头构图都不一样，**是玩法决策不是还原**，等顾客状态机写出来一起定。

#### 场景根下

| 节点 | Position (x, y, z) | Rotation | Scale | 备注 |
|---|---|---|---|---|
| `Main Camera` | `(-10.4, 10.5, 10.4)` | `(-35, -45, 0)` | `(1,1,1)` | 场景里已经是这个值，配完锁住（§3） |
| `Main Light` | 任意 | `(-50, -30, 0)` | `(1,1,1)` | 方向光的位置不影响光照（§4） |
| `Kitchen` | `(0, 0, 0)` | `(0,0,0)` | `(1,1,1)` | 空节点 |
| `Actors` | `(0, 0, 0)` | `(0,0,0)` | `(1,1,1)` | 空节点 |

#### `Kitchen` 底下

| 节点 | Position | Scale | 实际占地 |
|---|---|---|---|
| `Floor` | `(0, -0.05, 0)` | `(8, 0.1, 6)` | x −4→4, z −3→3 |
| `Wall_N` | `(0, 1.25, -3.1)` | `(8.2, 2.5, 0.2)` | 内表面在 z = −3 |
| `Wall_E` | `(4.1, 1.25, 0)` | `(0.2, 2.5, 6)` | 内表面在 x = 4 |
| `Station_Fridge` | `(2, 0.45, -2.5)` | `(1, 0.9, 1)` | x 1.5→2.5, z −3→−2 |
| `Station_Grill` | `(-2, 0.45, -2.5)` | `(1, 0.9, 1)` | x −2.5→−1.5, z −3→−2 |
| `Station_Assembly` | `(-3.5, 0.45, 0)` | `(1, 0.9, 1)` | x −4→−3, z −0.5→0.5 |
| `Station_Serve` | `(-1, 0.45, 2.5)` | `(2, 0.9, 1)` | x −2→0, z 2→3 |

> **这套 x 是按场景里那台相机（yaw = −45，从西南往东北看）定的**，墙在**北 + 东**。
> 如果以后把相机改成 `(15,15,15)` / `(-35, 45, 0)`（从东南看），
> 把上表所有 x 取负、`Wall_E` 改回 `Wall_W` 即可 —— 镜像不改任何两点间距离，
> `pnpm layout` 的难度判据两套都过（实测过）。

> ⚠ **`Floor` 的 y 是 −0.05 不是 0**。Cube 的原点在几何中心，厚 0.1 的地板要让**顶面**落在
> `y = 0`（§1 的约定），中心就得沉下去半个厚度。填 0 的话顶面在 +0.05，
> §6 那张 `y = 0.01` 的阴影片会陷进地板里，画面上是一片闪烁噪点，
> 而你会以为是阴影没做对 —— 其实是地板高了 5 厘米。
>
> ⚠ 工位的 y 都是 **0.45**（高 0.9 的一半），底面正好贴地。同理墙是 **1.25**（高 2.5 的一半）。

#### `Actors/Player` 底下

`Player` 本身放 `(0, 0, 0)`（脚底在地板上，出生在厨房正中）。

| 子节点 | Position | 目标真实尺寸 | Scale 怎么填 |
|---|---|---|---|
| `Body` | `(0, 0.6, 0)` | 直径 0.7 × 高 1.2 | 用 `_Ruler` 量出 Capsule 默认尺寸再除（见 §2.2） |
| `Head` | `(0, 1.4, 0)` | 直径 0.4 | Sphere 默认直径 1 米的话就是 `(0.4, 0.4, 0.4)` |
| `Anchor_Hand` | `(0, 1.75, 0)` | — | 空节点，持有物挂这儿（头顶上方） |
| `Shadow` | `(0, 0.01, 0)` | 0.8 × 0.6 米 | Plane 默认 10 米的话就是 `(0.08, 1, 0.06)` |

总身高 1.6 = 胶囊 1.2 + 球头 0.4，玩家直径 0.7（§7）。
`Body`/`Head` 的 scale 我给不了确切数 —— 它取决于内置 Capsule/Sphere 的默认尺寸，
**这个只有你的编辑器能量**（§2.2 的 `_Ruler` 就是干这个的）。位置和目标尺寸是定的。

#### `Canvas` 底下

先去 **项目 → 项目设置 → 项目数据 → 设计分辨率** 改成 **1280 × 720**（工程现在还是默认值），
适配选 **Fit Height** —— 横屏手机比例从 16:9 到 20:9 都有，锁高度、让宽度随比例延展最稳。

| 节点 | 尺寸 | 定位 | 备注 |
|---|---|---|---|
| `UI_HUD` | 跟随全屏 | `Widget` 四边都设 0 | 订单/金币/计时的 `Label` 放它下面 |
| `UI_ActionButton` | 160 × 160 | `Widget` 锚右下，`right = 120`、`bottom = 120` | 视觉指示而已，整个右半屏都能点 |
| `UI_Joystick` | 180 × 180 | 不锚定，脚本运行时移到手指位置 | **编辑器里 `active` 关掉**，浮动摇杆按下才出现 |

`UI_Joystick` 的 180 = `DEFAULT_STICK.radius` 90 的两倍（`API.md` 的 `input.ts` 一节）。

> ⚠ **`splitX` 别写死 640**。`TouchRouter` 的 `splitX` 用的是**触摸像素坐标**，不是设计分辨率。
> 运行时取 `view.getVisibleSize().width / 2`，否则在非 16:9 的手机上左右半屏的分界会跑偏。

#### `Ortho Height` 该落在哪一档

§3 让你填 5 再看画面判断这个字段是半高还是全高。按这套 8×6 厨房 + 2.5 米墙、
相机 `(15,15,15)` / `(-35,45,0)` 算出来，画面要装下的纵向跨度是 **7.76 米**（横向 9.90 米，不吃紧）：

- 如果它是**半高** → 最终会落在 **4.3 左右**
- 如果它是**全高** → 最终会落在 **8.5 左右**

这两个数的用途是**交叉校验**：你调出来的值离这两个都很远（比如 20），
说明不是 `Ortho Height` 的问题，是相机的 `Rotation` 或 `Position` 填错了，回 §3 第 2 步重来。

#### 场景搭好之后：`pnpm scene` 把编辑器里的值读回来

`.scene` 是扁平化的 JSON，`tools/scenedump.ts` 能直接解析。搭完（或搭到一半）跑：

```
pnpm scene                    # 默认读 game/assets/Main.scene，没有就退回 test.scene
pnpm scene <路径>
```

它打印层级树、每个节点的 Transform、相机与光的全部参数、Skybox/Shadows 状态，
然后自动对三件事：

1. **§0 三条红线** —— 有没有物理组件、有没有实时阴影、Skybox 有没有贴图（有就退出码 1）
2. **与 §2.3 定稿逐项对比** —— 七个节点的 Position / Scale 哪个对不上，直接报出来
3. **反向生成 `PLACED`** —— 把场景里工位的实测坐标打成可以直接贴进 `tools/layoutcheck.ts` 的片段

所以 §11 那十条验收里，原本「只能靠眼睛看」的那几条现在大半是机器判的。
**每次改完场景推上来跑一次**，比事后追查便宜得多。

4. **材质** —— 顺着 `MeshRenderer` 的 uuid 找到 `materials/*.mtl`，
   把挂载对不对、`mainColor` 的 rgba、`Technique` 是不是 transparent 逐个对 `MAT_SPEC`。
   还挂着默认材质的会点名报出来

⚠ 它读不出来的：内置 Capsule/Sphere 的默认尺寸（不在工程里，所以 `Body`/`Head`
的真实米数还是要你用 `_Ruler` 量），以及画面本身 —— 颜色搭不搭、够不够跳，判据管不了。

#### 反过来写：`pnpm scene:apply`

上面那套定稿数值不用手填 —— `tools/sceneapply.ts` 直接写进 `.scene`：

```
pnpm scene:apply            # dry-run，列出将要改的每一项
pnpm scene:apply --write    # 落盘
```

数值来自 `tools/scene-spec.ts`，`scenedump` 拿它做对比、`sceneapply` 拿它做写入 ——
**一份真相，不会一边改了另一边忘了**。

它只碰**纯数值和名字**：Transform、节点名、相机 `ClearFlags`、Skybox 开关与 cubemap 引用。
**加组件、改 `SizeMode`、挂材质、调 `OrthoHeight` 都不在里面** ——
那些要动条目结构和资源引用，编辑器里点比脚本安全。

两条使用前提：

1. ⚠ **跑之前把 Cocos 关掉。** 编辑器内存里有一份场景，它一保存就把脚本写的盖掉。
2. 写入前脚本自己有个活性守卫：先验证「原样读进来再写出去」逐字节无损，
   不无损就中止 —— 否则 diff 会混进一堆无关的浮点格式噪声，改动没法复核。
   （Node 的 `JSON.stringify` 对这份文件正好是无损的，Python 的不是，会把 `0.00001` 写成 `1e-05`。）

#### 这套坐标是怎么来的：`pnpm layout`

工位摆位不是布置家具，它直接决定跑腿距离，而**跑腿是这个游戏的瓶颈**（M1 实测结论）。
`difficulty.ts` 那条 20 天难度曲线是拿 `defaultSimConfig().layout` 标定出来的 ——
场景一摆就换了一套坐标，那条曲线还成不成立必须验。

`tools/layoutcheck.ts` 就是这个判据，两组：

| 组 | 查什么 |
|---|---|
| **几何** | 工位不出界；与边界要么贴死要么留够 1.5m（中间那档是卡人的死角）；两两之间**欧氏**间隙 ≥1.5m；六条工位间直线都不穿过第三个工位 |
| **难度** | 拿这套坐标跑 20 天曲线，与 M1 标定布局比完成率、后期完成率、`idle` |

跑出来是：

```
── 几何判据    OK：边界、通道 ≥1.5m、动线不穿模，全部通过
── 难度判据    M1 基线    完成率 92.4%  后期 83.6%  idle 70.8s  带外 0 天
              场景摆位   完成率 92.6%  后期 84.7%  idle 70.2s  带外 0 天
              偏差：idle -0.9%  后期完成率 1.1pt
```

**摆位一动就重跑它**（M3 那个「工位间距」旋钮也归它管）。三条实测教训写在这儿，免得重犯：

1. **「一圈路径长度」不是可靠指标。** 试过一套一圈同为 17.20m 的摆位，后期完成率掉到 59.9%——
   真实动线是冰箱↔烤炉↔组装台之间的**往返**，不是绕场一圈。
2. **距离长 9% 会让完成率掉 27pt。** 第一版摆位一圈 18.80m（+9.2%），
   第 18–20 天完成率从 83.6% 掉到 56.1%，8 天掉出难度带。
   放大得这么厉害是因为后期 `idle` 已经见底，多跑的每一米直接变成超时。
3. **几何判据和难度判据互相不能替代。** 上面那套烂摆位**几何全部通过**，只是难度崩了；
   反过来也有几何过不了但难度没问题的。两组都要跑。

> `idle`（玩家空闲秒数）是最灵敏的一维 —— 完成率还没动的时候它已经先动了。
> 判据里它的阈值定得最紧（偏离基线 >10% 就报），就是这个原因。

## 3. 相机：斜 45° 怎么配

### 用正交（Ortho），不用透视

| | 正交 | 透视 |
|---|---|---|
| 远近物体大小 | 一样 | 近大远小 |
| 摇杆方向映射 | **屏幕方向 ↔ 世界方向恒定** | 随位置微变 |
| 「一眼看全厨房」 | 调一个 `Ortho Height` 就够 | 要同时调 FOV 和距离 |

正交是这类游戏的默认答案，也让 `input.ts` 里那套 camera-relative 映射**在全屏任何位置都成立**。

### 配置步骤（按顺序做，别跳）

1. 选中 `Main Camera` → Inspector 的 `Camera` 组件 → **`Projection` 改成 `ORTHO`**
2. **`Rotation` 先填 `(-35, 45, 0)`** ——
   - `-35` 是俯视角（负值往下看）。数学上的等距投影是 `-35.264°`（`arctan(1/√2)`），
     游戏里 30–45 都常见，先用 35
   - `45` 是绕 Y 的偏航，斜 45° 的「45」就是这个数
   - ⚠ **填完看场景视图确认是从右上方往下看**。如果方向不对，是欧拉角顺序的问题，
     把 45 改成 -45 或 135 试，**不要靠推理，看着调**
3. **`Position` 填 `(15, 15, 15)`** ——
   正交相机的位置**不影响能看到多大范围**，只影响看向哪里和裁剪。
   放远一点纯粹是为了别把厨房裁掉
4. **`Near` 填 `1`、`Far` 填 `100`** —— 相机在 (15,15,15) 距原点约 26 米，这个范围包得住
5. **`Ortho Height` 先填 `5`，然后调到「一眼看全厨房」** ——
   ⚠ 这个字段是**半高还是全高**，你填 5 看一眼就知道了：如果画面纵向覆盖约 10 米就是半高，
   约 5 米就是全高。**知道了把结论写进这一节**，省得下次再试
6. 调好之后 **在层级管理器里锁住 `Main Camera`**（节点右侧的小锁图标），
   防止后面拖别的节点时手滑把相机拖跑

### 相机是固定的，这是硬约束

ROADMAP §1「轻 3D 的精确落点」定死了：**固定角度、固定或轻微跟随位移，不可旋转、不可缩放。**
不是做不到，是一旦可旋转，`input.ts` 的 yaw 就变成每帧要读的动态值、
角色被家具挡住要写描边 shader、还要做相机碰撞——三样工作凭空长出来，
换来的是这个游戏根本不需要的自由度。

### 真机第一件事：验 yaw 的符号

`API.md` 里写了，这里再说一遍，因为它是**唯一一个我在服务器上验不了的输入层参数**：

> 上下左右各推一次摇杆，看角色往哪走。
> **前后反了** → 把传进 `stickToWorld` 的 yaw 取负。
> **左右反了** → 相机是往另一边转的，同样取负。
> 代码里锁死的是「先旋转再移动」这个结构，不是某个具体符号。

## 4. 光照：一盏灯，别开阴影

M2 只要能看出「这是个三维的盒子」就够了。

1. 场景里保留默认的 `Main Light`（`DirectionalLight`），**`Shadow Enabled` 不勾**
2. `Rotation` 大约 `(-50, -30, 0)`，让光从斜上方来 ——
   **别让光的方向和相机方向重合**，重合了每个面亮度一样，立体感全没了，
   看起来就像贴纸。这是最容易犯的一个，而且很难自己发现
3. `Color` 保持白、`Intensity` 默认。真要调等有了美术再说
4. **环境光**：点击层级管理器最顶上的场景节点 → Inspector → `Ambient` 分组 →
   `Sky Color` / `Ground Color` 用**纯色**。
   ⚠ **不要在 `Skybox` 里指定 cubemap 贴图，也不要勾 HDR**——红线 3，850 KB

阴影靠 §5 的贴片，不靠灯。

## 5. 材质：M2 阶段的做法

### 纯色，零贴图（现状：八个都建成了 `builtin-unlit`）

- 资源管理器右键 → **创建 → 材质** → Inspector 里选 `Effect`
- 只改基础色，**别挂任何贴图**。⚠ 属性名跟着 `Effect` 变：
  `builtin-unlit` 是 **`mainColor`**，`builtin-standard` 是 **`albedo`**
- 做完拖到节点 `MeshRenderer` 组件的 `Materials[0]` 上

> ⏳ **`unlit` vs `standard` 待你看画面拍板**（2026-09-07）。
> 八个材质现在全是 `unlit`：不受光照，填什么色就渲染出什么色，
> 省掉「场景偏暗是光的问题还是材质的问题」这类查不动的问题。
> 代价是**六个面同色** —— 斜 45° 看过去，Cube 的三个可见面完全一样亮，立体感只剩轮廓。
> 想要那点明暗，把七个不透明材质换成 `standard`（`M_Shadow` 必须留 `unlit`，阴影不该受光）。
> 换与不换都行，但**别混着来** —— 一半受光一半不受光，同一个灰在两个工位上会差出一档。

**为什么不挂贴图**：纯色材质的包体几乎为零，一张 512×512 的 PNG 就是几十到几百 KB。
主包只剩约 1668 KB 给内容（§2.4a），M2 一张贴图都不该有。

### 建几个材质？

**别为 draw call 提前优化。** §2.2 算过：即使一行不优化也只有 90–125 个 draw call，
红线是 200，优化后能到 12–20。M2 阶段建 8–12 个材质完全没问题。

一个够用的配色（能一眼分清工位就行，不用好看）：

| 材质 | 用途 | 建议色 |
|---|---|---|
| `M_Floor` | 地板 | 浅灰 |
| `M_Wall` | 两面墙 | 更浅的灰（和地板要分得开） |
| `M_Fridge` | 冰箱 | 蓝 |
| `M_Grill` | 烤炉 | 深红 / 橙 |
| `M_Assembly` | 组装台 | 木黄 |
| `M_Serve` | 出餐口 | 绿 |
| `M_Player` | 玩家 | 亮色（在所有背景上都要跳出来） |
| `M_Shadow` | 贴地阴影 | 黑，半透明 |

> ⚠ **颜色不是随便挑的那一条**：玩家角色的颜色必须在**所有**工位颜色上都能一眼看见。
> 你在编辑器里看是清楚的，因为你知道它在哪；真机上手忙脚乱时找不到自己在哪，
> 是这类游戏最常见的早期反馈。

### 贴图什么时候才需要设压缩格式

现在不需要（没有贴图）。但**一旦开始导入贴图**，规矩是：
资源管理器选中图片 → Inspector 右上角选平台 → 压缩格式选 **ASTC**（A6 已定）。
默认的 PNG 会让包体和内存都翻倍，而 iOS 内存是这个项目最可能真机闪退的地方（§2.5）。

## 6. Blob Shadow：贴地椭圆，不是实时阴影

角色脚下一个椭圆暗斑，成本几乎为零，但**它是「角色到底站在哪」的唯一视觉线索**——
斜 45° 下没有影子，角色看起来像浮在空中，玩家会一直走不准位置。这不是装饰，是功能。

M2 最省事的做法（不需要贴图）：

1. 角色底下建一个 `Plane`（3D 对象 → Plane），命名 `Shadow`
2. `position.y` 抬一点点 —— **不能是 0**，和地板同高会 z-fighting（画面上一片闪烁的噪点）。
   场上定稿值是 `0.006`（编辑器里试出来的，够躲开 z-fighting 又不至于看着飘）
3. `scale` 压成椭圆 —— ⚠ **Plane 的内置 mesh 默认边长是 10 米**（§2.2 的「米尺」那条），
   所以要的是 `(0.08, 1, 0.06)` 而不是 `(0.8, 1, 0.6)`。
   填成后者会铺出一张 8×6 米的黑片把整个地板盖住，看起来像「材质坏了」，其实是尺寸差 10 倍。
   拿 `_Ruler` 比一下：影子该比角色略大一圈，不该比工位还大
4. 材质 `M_Shadow`：`Effect` 选 `builtin-unlit`（阴影不该受光）、
   `Technique` 选 **transparent**、`mainColor` 黑色、**Alpha `76`**（= 0.3 × 255）。
   ⚠ 这三样缺一，出来就是一块**不透明纯黑片**：`opaque` 下 alpha 被整个忽略，
   Alpha 拉到多低都没用。`pnpm scene` 会把 Technique 和 Alpha 一起报出来
5. ⚠ Plane 默认是水平的（法线朝 +Y）。如果发现它立着，绕 X 转 `-90`

有贴图之后可以换成一张 64×64 的径向渐变 PNG，边缘会柔和很多。M2 不做。

## 7. 尺寸建议：通道宽度是手感的关键

按 §2.2 的规模（8m × 6m 厨房）：

| 物件 | 尺寸（米） | 说明 |
|---|---|---|
| 地板 | 8 × 6 | **Cube**，scale `(8, 0.1, 6)`（别用 Plane，默认 10 米见 §2.2） |
| 墙高 | 2.5 | 只要挡住视线边界，不用很高 |
| 工位（冰箱/烤炉/组装台） | 1.0 × 0.9 × 1.0（宽×高×深） | 一个 Cube 压一下就行 |
| 出餐口 | 2.0 × 0.9 × 1.0 | 是个柜台，比别的宽，顾客在外侧 |
| 玩家半径 | **0.35** | 直径 0.7 |
| 玩家身高 | 1.6 | 胶囊 1.2 + 球头 0.4 |

> ### ⚠ 通道宽度 ≥ 1.5 米，这条最影响手感
>
> 玩家直径 0.7 米。通道留 1.0 米时，看起来「明明过得去」，
> 实际因为摇杆输入是连续方向、不是网格对齐，玩家会不停蹭到工位边缘被推开——
> **表现是「操作很黏」，但玩家不会说是通道窄，只会说这游戏手感差。**
>
> 留 1.5 米（约两倍直径）是安全值。**M2 摆位就按这个来，别等做完再改**——
> 工位一旦摆定，`logic/` 那边的坐标、单测、难度曲线都跟着定了，回头改是一串连锁修改。

> **工位深度为什么是 1.0 而不是 0.8**：§1 要求坐标落在 0.5 网格上。深 0.8 的话，
> 工位要贴住 `z = -3` 的墙，中心就得填 `-2.6` —— 网格一破，后面每个坐标都得手算。
> 深度取 1.0，贴墙就是 `-2.5`，全套坐标都是 0.5 的倍数。
> 出餐口 2.0 宽也是同理（1.2 宽的中心会落在 0.1 网格上）。

摆位建议：四个工位**别摆成一条直线**。玩家在冰箱和烤炉之间来回跑是这个游戏的主要动作，
摆成一条线的话走位没有任何决策；摆成 L 形或散在四角，「先拿哪个」才有得想。

**具体摆哪儿别自己试** —— §2.3 给了一套枚举出来、并用 `pnpm layout` 验过难度的定稿坐标。
自己挪的话记得跑一遍那个判据：实测过一套看起来很合理的摆位让后期完成率掉了 27 个百分点。

## 8. 工位怎么和 `logic/` 对齐：**尺寸只能有一个来源**

这是整份文档里最容易出 bug 的一条。

`logic/types.ts` 的 `Station` 需要 `pos` / `box`（AABB）/ `triggerRange`。
**如果编辑器里方块的尺寸和代码里的 AABB 各写一份，它们迟早会不一致**，
表现是「角色卡在看不见的墙上」或「明明贴着灶台却提示够不着」——
而且这类 bug 极难查，因为画面上一切正常。

**做法：代码从节点读尺寸，不在代码里写第二份数值。**

你在编辑器里要保证的只有三件事：

1. 工位节点命名 `Station_<名>`（`Station_Fridge` / `Station_Grill` / `Station_Assembly` / `Station_Serve`）
2. 工位的**几何中心就是节点原点** —— 别把 Cube 在子节点里偏移。
   偏移了的话节点 position 不等于方块中心，读出来的 AABB 就是错的
3. 缩放**只用节点的 `scale`**，别去改 mesh 的尺寸参数。两个地方都能改尺寸，只用一个

我这边写 `StationView` 组件读 `node.worldPosition` 和 `node.scale` 生成 `Station`。
**你摆完位置告诉我一声，我把组件写好你拖上去。**

## 9. 编辑器操作技巧

### 高频快捷键

| 键 | 作用 |
|---|---|
| `W` / `E` / `R` | 移动 / 旋转 / 缩放 |
| `F` | 聚焦到选中节点（找不到节点在哪时按这个，比手动拖视图快得多） |
| `Ctrl` + `D` | 复制节点（摆四个工位时用） |
| `Ctrl` + `Z` | 撤销 —— ⚠ **场景和资源的撤销栈是分开的**，改了材质再撤销可能撤的是场景 |

### 实用习惯

- **摆位时用顶视图**：场景视图右上角的坐标轴 gizmo 点 `Y` 轴切到俯视。
  斜视图下拖东西很难拖准，俯视图下 X/Z 一目了然
- **改的是编辑器视图，不是 Main Camera**：切视角、滚轮缩放动的都是编辑器的观察视角，
  游戏里看到的永远是 `Main Camera`。**要确认玩家看到什么，用预览（播放按钮）**
- **建好就锁**：`Main Camera`、`Floor`、两面墙都锁上（层级管理器节点右侧小锁）。
  这几样建完不再动，锁了能省掉大量误拖
- **改 Prefab 要进 Prefab 编辑模式**：双击 prefab 资源进去改，改完保存。
  在场景里直接改的是**实例**，不会同步回 prefab——这是 Cocos 最常见的「我明明改了却没生效」
- **Inspector 里数值可以拖着改**：鼠标按住字段左边的标签左右拖，比反复输入快

### ⚠ 场景文件不 merge（ROADMAP §6.5）

`.scene` 是 JSON，但**是编辑器生成的、带 uuid 的 JSON，git 冲突了没法手动合**。
所以：

- **同一时间只有一个人改场景**（这个项目里就是你）
- 我不碰 `.scene` / `.prefab` / `.meta`
- 你改场景之前 `git pull`，改完尽快 commit，别攒着

### 每次开工 30 秒

```bash
git pull
pnpm test          # 逻辑层没坏，才值得开编辑器
# → 然后再启动 Cocos Creator
```

逻辑层跑一次 1.3 秒、154 个测试。开编辑器要半分钟起。顺序反了会浪费很多时间。

## 10. 常见坑速查

| 现象 | 真因 | 修 |
|---|---|---|
| 画面一片闪烁噪点 | 两个面同高度 z-fighting | 阴影片 `y=0.01`，地板和贴片错开 |
| 方块看起来是平的、没立体感 | 材质是 `unlit`（现状就是），六面同色；或光的方向和相机方向重合 | 见 §5 那条待拍板；光转到 `(-50,-30,0)` 一带 |
| 影子是一块不透明纯黑 | `M_Shadow` 的 `Technique` 还是 `opaque`，alpha 被忽略 | 切 transparent，`mainColor` 的 Alpha 设 `76` |
| 角色看不见 / 找不到自己在哪 | 玩家颜色和某个工位或地板太接近 | 换成在所有背景上都跳出来的亮色 |
| 「操作很黏」，老是蹭到东西 | 通道窄于 1.5 米 | 重摆工位。**越早改越便宜** |
| 角色像浮在空中 | 没有 Blob Shadow | §6 |
| 地板整块变黑 / 影子大得离谱 | Plane 默认 10 米，scale 少除了个 10 | §6 第 3 步 |
| 3D 全没了只剩 UI，或 UI 被 3D 盖住 | 动了 Canvas 自带那个相机的 `ClearFlags` | §2.2「Canvas 会自带一个相机」 |
| 动作键点一次响应两次 | `UI_ActionButton` 挂了 `Button` 组件，和 `TouchRouter` 抢事件 | 摘掉 Button，只留 Sprite（§2.2） |
| 改了 prefab 没生效 | 改的是场景里的实例 | 双击 prefab 进编辑模式改 |
| 相机莫名跑偏 | 拖别的节点时手滑拖到了相机 | 锁住 `Main Camera` |
| 构建后包体突然大了几百 KB | 挂了贴图 / 指定了 skybox cubemap / 加了物理组件 | 跑 `pnpm size` 对比，看是哪一栏涨的 |
| 编辑器里好看，真机上看不清 | 手机屏小、亮度低、还有反光 | **只信真机截图**，编辑器里的观感不作数 |

## 12. 摆完之后告诉我什么

§2.3 的坐标已经由 `pnpm scene:apply --write` 写进场景了，所以你要回报的不是「你摆成什么样」，
而是**哪几处你又动过**，外加两个只有编辑器能量出来的数：

1. **`Ortho Height` 最后填的值，以及它是半高还是全高**（§3 步骤 5 / §2.3 末尾的交叉校验）
2. **`Body` / `Head` / `Shadow` 最后填的 Scale**（取决于内置 Capsule/Sphere/Plane 的默认尺寸，我这边量不到）
3. 如果你挪了任何工位 —— 新坐标，**并且跑一遍 `pnpm layout`**（改 `tools/layoutcheck.ts` 顶上的 `PLACED`）
4. 如果地板没按 8×6 —— 实际尺寸

**脚本改不了、必须你在编辑器里做的**（`pnpm scene` 会一直报到做完为止）：

- **加组件** —— `UITransform` / `Widget` 这类要新增条目并重排引用 id，编辑器里点比脚本安全
- **材质挂载** —— 八个都建好了；⚠ `Body` / `Head` 还挂着默认材质，要挂 `M_Player`（色值见 §2.3）
- **`Body` / `Head` 的 Scale** —— 取决于内置 Capsule/Sphere 的默认尺寸，工程里没有这个数
- **`Ortho Height`** —— 要看画面调

组件加好之后，它身上的**数值**（`contentSize`、`SizeMode`、Transform）就归 `scene-spec.ts` 管了，
跑 `pnpm scene:apply --write` 填，别手填 —— 手填的值没有判据守着，下次谁动了都不知道。

> ⚠ `Sprite` 的 `SizeMode` 和 `contentSize` **必须一起改**。
> SizeMode 不是 `CUSTOM` 时，编辑器一加载就拿图片尺寸把 `contentSize` 顶回去（内置白块是 40×36），
> 只改尺寸等于没改。`sceneapply` 两个一起写，`scenedump` 两个一起查。

直接把这几个数贴给我就行，**不用截图**——我读不了编辑器，但读得懂数字。
拿到之后我写 `StationView` 组件把 `kitchen.ts` 的坐标接上。
