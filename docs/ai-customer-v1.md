## 1. 地基：机制层 / 表演层分离

这是整个系统唯一不能妥协的设计。

### 问题

原稿的吸血鬼顾客说：

> 不要蒜 / 不要洋葱 / **不要阳光种植番茄**

前两条引擎能判定（食材集合里查有没有）。第三条判不了——游戏里没有「阳光种植」这个概念。
玩家做完汉堡端上去，系统凭什么算他成功还是失败？

**AI 能生成的需求 ≠ 引擎能判定的需求。** 不切开这两者，要么笑点被砍光（只让 AI 说引擎懂的话），
要么游戏没法判定（AI 想说啥说啥）。

### 解法

一张顾客卡分两层，物理上是两组字段：

| | 机制层 (mechanics) | 表演层 (flavor) |
|---|---|---|
| 内容 | `required` / `banned` / `doneness` / `patience` | `identity` / `lines.*` |
| 取值 | **封闭词表 + 枚举**，schema 强制 | 自由文本 |
| 谁读 | 游戏引擎，用于判定成败 | 玩家，用于笑 |
| 能不能越界 | 不能（JSON Schema `enum` 拦截） | 随便 |

吸血鬼那一单落地成：

```json
{
  "identity": "吸血鬼伯爵",
  "order": { "required": ["bun","patty"], "banned": ["onion","tomato"], "doneness": "rare" },
  "lines": { "order": "不要洋葱。也不要番茄——尤其阳光底下长的那种。肉，三分熟。" }
}
```

玩家听到的是梗，引擎判定的是 `banned: [onion, tomato]` + `doneness: rare`。两边都成立。

### 生成时的铁律

> **`lines.order` 是 `order` 字段的人话包装。**
> 它可以用任何离谱的说法去描述这些食材和火候，
> 但**不能引入机制层不存在的要求**。
> 玩家只要满足了机制层，判定就必须是成功。

反例（生成时要拒绝的）：

| 违规台词 | 为什么违规 |
|---|---|
| 「再给我一杯血腥玛丽」 | 引入了词表外的物品，玩家做不出来 |
| 「装盘时摆成五芒星」 | 引入了机制层没有的摆盘维度 |
| 「你猜我要什么」 | 需求不可知，玩家无法完成 |
| 「随便，看着办」 | 同上。想表达随性，就用宽松的 `required` + 台词写随性 |

## 2. 封闭词表（V1）

### 食材 `INGREDIENTS`

| key | 中文 | 角色 |
|---|---|---|
| `bun` | 面包 | 骨架，恒在 `required` |
| `patty` | 牛肉饼 | 骨架，恒在 `required` |
| `cheese` | 芝士 | 可选 |
| `lettuce` | 生菜 | 可选 |
| `tomato` | 番茄 | 可选 |
| `onion` | 洋葱 | 可选 |
| `pickle` | 酸黄瓜 | 可选 |
| `bacon` | 培根 | 可选 |

> GDD 原稿第一版只写了 面包/牛肉/芝士 三种。**V1 这里扩到 8 种是刻意的**：
> 只有三种食材时 `banned` 毫无意义（禁掉任一样汉堡就不成立），
> 而「我都说了不要洋葱」正是评价系统最有梗的一类反馈。
> 6 个可选配料够 `required`/`banned` 玩出组合，又不至于让阶段 2 的厨房布局爆炸。

### 火候 `DONENESS`

`rare`（三分） / `medium`（五分） / `well`（全熟）

对应烤炉计时窗口。这是「牛肉火候完美 +20」这条评价的机制来源。

### 情绪 `MOOD`

`cheerful` / `grumpy` / `anxious` / `dreamy` / `menacing` / `heartbroken` / `manic` / `deadpan`

引擎用它选表情图和 BGM 变体；生成时用它定台词语气。

## 3. 顾客卡 Schema

完整定义见 [`../schema/customer.schema.json`](../schema/customer.schema.json)（可直接作为 `output_config.format` 的 json_schema 使用）。

```jsonc
{
  "id": "c_0001",

  // ── 机制层：引擎判定 ──
  "order": {
    "required":  ["bun", "patty", "cheese"],   // enum 限定，必含 bun+patty
    "banned":    ["onion"],                    // enum 限定，与 required 不得相交
    "doneness":  "medium",
    "patience":  45                            // 秒，引擎倒计时
  },

  // ── 表演层：玩家阅读 ──
  "identity": "吸血鬼伯爵",                      // ≤10 字
  "mood": "menacing",
  "lines": {
    "greet":       "……这里有活人吗。",            // ≤12 字
    "order":       "不要洋葱。肉要三分熟，能滴血的那种。",  // ≤30 字 ★主笑点载体
    "wait_nudge":  "太阳快出来了。",              // ≤15 字
    "praise":      "比 1823 年那顿好。",          // ≤20 字
    "complain":    "我说了不要洋葱。你想我死？"      // ≤20 字
  },

  // ── 长线（可空）──
  "arc": null   // 或 { "series_id": "homeless_guy", "chapter": 1, "unlock_day": 1 }
}
```

### 字数上限不是排版洁癖

**两个核心系统在抢玩家的注意力：** 厨房混乱系统的目标是「让玩家手忙脚乱」，
而 AI顾客系统需要玩家「读完并笑」。玩家一边跑冰箱一边烤肉时，**没有一秒钟能读长台词**。

所以：笑点必须能在 30 字内落地，且优先压进 `order` 那一句——因为那句玩家**必须**读（不读做不出来）。
其余四句是锦上添花，玩家可能压根没看。

这条约束反过来是个筛选器：如果一个梗必须铺陈 100 字才好笑，它在这个游戏里就是不成立的梗。

## 4. 反同质化：维度组合，不是自由发挥

**别让 AI「生成 200 个有趣的顾客」。** 它会收敛到均值——你会得到 200 个语气雷同的「奇怪顾客」，
读到第 20 张就腻了。这是 LLM 批量创作的固有失败模式。

**做法：代码随机抽正交维度，AI 只负责把抽到的组合写活。**

| 维度 | 说明 | 示例值 |
|---|---|---|
| `archetype` 身份原型 | 他是什么 / 从哪来 | 吸血鬼、唐朝穿越者、外卖骑手、AI机器人、退休特工、幼儿园老师、末日幸存者、选秀练习生 |
| `obsession` 执念 | 驱动奇怪需求的东西 | 养生、复仇、减肥、迷信、洁癖、怀旧、攀比、赶时间 |
| `mood` 情绪 | 当下状态 | 见 §2 `MOOD` |
| `voice` 说话方式 | 语言风格 | 文言文、播音腔、说唱、命令句、气声、全用问句、客服话术、方言 |

各 20 个值 → **160,000 种组合**。碰撞会撞出人写不出来的东西：

> `archetype=唐朝穿越者` × `obsession=减肥` × `mood=anxious` × `voice=客服话术`

维度池维护在 [`../prompts/dimensions.json`](../prompts/dimensions.json)，扩池只需往里加值。

**每次生成请求传入一组已抽好的维度**，AI 不选维度，只写内容。这样重复率由随机数保证，不由模型的想象力保证。

## 5. 成本架构：AI 是内容管线，不是运行时服务

### 为什么不能运行时调

> DAU 1000 × 20 单/人/天 = **20,000 次调用/天**
> Haiku 4.5 + prompt caching，每次约 $0.0014
> → **$28/天 ≈ $850/月**

一个未验证的微信小游戏付不起，也不该付。

### 三条路径

```
┌─ 离线·一次性 ────────────────────────────────────┐
│ 最强模型 + Batch API(5折) → N 张顾客卡 JSON       │
│ → 校验 → 打进包体 / 传 CDN                        │
└──────────────────────────────────────────────────┘
┌─ 运行时·每局 ────────────────────────────────────┐
│ 本地随机抽卡 + 变量填充 → API 调用 0 次 → $0      │
└──────────────────────────────────────────────────┘
┌─ 实时·低频 ──────────────────────────────────────┐
│ 仅长线剧情推进（§6）→ Haiku 4.5 + caching        │
│ 1.5 次/玩家/天 → 约 $2/天 @DAU 1000              │
└──────────────────────────────────────────────────┘
```

### 离线生成算账

单张卡：input ≈ 1,200 tok（system + 词表 + 维度），output ≈ 750 tok。
Batch API 一律 5 折。

| 模型 | 单价(in/out per MTok) | Batch 后 | 单张 | **200 张（验证）** | 10,000 张（上线） |
|---|---|---|---|---|---|
| Claude Opus 5 | $5 / $25 | $2.5 / $12.5 | $0.0124 | **$2.5** | $124 |
| Claude Sonnet 5 | $2 / $10 ※ | $1 / $5 | $0.0050 | $1.0 | $50 |
| Claude Haiku 4.5 | $1 / $5 | $0.5 / $2.5 | $0.0015 | $0.3 | $15 |

※ Sonnet 5 引导价 $2/$10 有效期至 **2026-08-31**，之后回到 $3/$15。想省这一档就趁现在跑。

**关于那 750 tok output**：卡片 JSON 本身只有约 350 tok，其余是 thinking——Opus 5 和 Sonnet 5
默认开思考，且 thinking token 按 output 计费。生成脚本默认 `effort: "low"` 就是为了压这部分；
写一张顾客卡不需要深度推理，实测若发现 low 下创意明显变差，再往上调一档并接受成本翻倍。
Haiku 4.5 默认不思考，所以它那行是纯 JSON 的成本。

**建议：验证阶段用 Opus 5。** 全部成本 $2.5——省这个钱毫无意义，而创意质量直接决定项目生死。
等 §7 的判据过了、要扩到 10,000 张时，再拿 Opus 5 的产出当 few-shot 去跑 Sonnet 5 压成本。

> Haiku 4.5 便宜 5 倍，但「好笑」恰好是小模型最弱的一环。**这一环不要省。**

### 工程约束：微信小游戏不能直连 Anthropic API

1. **域名白名单** —— 小游戏 `wx.request` 只能访问已备案并在后台配置的域名，`api.anthropic.com` 加不进去。
2. **密钥泄露** —— 包体可解包，key 放前端等于公开。

所以实时那条路**必须经自研服务器中转**（低频，最小 VPS 足够）。
预生成的 JSON 是静态资源，走 CDN 或直接打进包，**不需要任何后端**——这是选预生成架构的额外收益。

## 6. 长线记忆：结构化 profile，不是塞历史

「第 1 天流浪汉 → 第 3 天找到工作 → 第 10 天带朋友 → 第 20 天结婚请客」。

### 两种实现，V1 用第一种

**A. 预写剧情线（V1 采用）**
一条 arc 就是一组按 `chapter` 排序的顾客卡，共享 `series_id`，由 `unlock_day` 控制出现时机。
**完全离线生成，运行时零调用。** 写 20 条 arc × 5 章 = 100 张卡，就够第一个月的故事感。

```json
{ "arc": { "series_id": "homeless_guy", "chapter": 3, "unlock_day": 10 } }
```

**B. 动态记忆（V2 再说）**
玩家行为影响剧情走向时才需要。届时的存档结构应该是：

```json
{
  "series_id": "homeless_guy",
  "chapter": 3,
  "facts": ["第1天给了免费汉堡", "第3天点了最贵的", "讨厌洋葱"],   // 结构化事实，≤10 条
  "sentiment": 72
}
```

**不要把玩家全部对话历史塞进 prompt。** 塞进去 token 数随天数线性增长，
第 30 天的调用会比第 1 天贵一个数量级。只传 profile + 最近 3 条事实。

## 7. 验证判据（阶段 1 的唯一交付）

生成 200 张卡，**不写游戏，纯文本读一遍**。三个可量化判据：

### 判据 1 · 截图率 ≥ 15%

200 张里，你会想截图发给朋友的有几张？

- **≥ 30 张（15%）** → 方向成立，进阶段 2
- **10–30 张** → 方向可救，调维度池和 prompt 再跑一轮
- **< 10 张（5%）** → **方向不成立**。厨房和动画救不了不好笑的卡，只会让它更贵

### 判据 2 · 重复感衰减点 ≥ 50 张

按生成顺序读，读到第几张开始觉得「又是这个套路」？
早于 50 张说明维度池太小或 prompt 引导太强，先扩维度再重跑。

### 判据 3 · 机制耦合率 ≥ 40%

有多少张卡的笑点**和订单内容真的有关**（`required`/`banned`/`doneness` 参与了梗）？

这条最容易被忽略，也最致命：**纯身份搞笑、订单却是普通汉堡的卡，玩家在游戏里看不到笑点**——
他正忙着跑冰箱，只会瞥一眼 `order` 那句。笑点没长在他必须读的那句话上，就等于不存在。

耦合率低时的修法：在 prompt 里加硬约束「执念必须体现为具体的食材增删或火候要求」。

> 三条都过了，才谈得上做厨房。任何一条不过，做厨房只是在给一个不好笑的核心加包装。

## 附：三个已知风险

| 风险 | 表现 | 应对 |
|---|---|---|
| **越界台词** | AI 在 `lines` 里提到词表外的食材/操作 | schema 拦不住自由文本，靠 `validate_customers.py` 做软扫描 + 人工抽查 |
| **梗的文化时效** | 网络梗 3 个月就过期 | 维度池里网络梗类值单独标记，便于定期换血；`archetype` 优先选长效原型 |
| **审核风险** | 微信小游戏内容审核，涉及宗教/暴力/擦边的身份会被驳回 | 维度池里剔除敏感值；生成后过一遍关键词黑名单再入包 |
